# ADR 0005 — Public market data; accounts for user-owned data; JWT access + rotating refresh cookie
Status: Accepted (defaults; revisit if the product becomes paid/multi-tenant)
**Decision.** Market data, analysis and scanners are public read. Watchlists and saved scans need an account.
Argon2id password hashes; 15-minute JWT access token; 14-day rotating refresh token in an
`HttpOnly; Secure; SameSite=Lax` cookie; roles `user`, `admin` (admin: trigger sync, ops endpoints).
Secrets only from env/Docker secrets; production refuses the dev default (`Settings.assert_production_safe`).

**Amendment (Phase 5) — what the defaults became.**
* **Refresh tokens** are opaque 256-bit random values; only their SHA-256 is stored (`refresh_tokens.token_hash`). Each use *rotates*: the presented token is spent and the next one issued in the same family. A spent token shown again **after a 10 s leeway window** means two parties hold it, so the **whole family is revoked** (theft detection). **Inside the window** it is exchanged once more by rotating its still-unused successor: browsers abort the response carrying the rotated cookie whenever a page is reloaded or left mid-refresh, which would otherwise sign the user out for nothing (found by the Playwright suite). If the successor was itself already spent, the replay is two tabs racing: a plain 401 that neither revokes the family nor clears the cookie (the newer cookie another tab received must survive). The trade-off: a thief holding a token that was rotated less than 10 s ago can still use it once, after which the chain moves on and the owner's next use hits the window logic again.
* **Cookie:** `HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth` (only auth endpoints ever see it), `Secure` automatically in production. CSRF is covered by `SameSite=Lax` plus POST-only JSON endpoints; there is no cookie-authenticated state-changing endpoint outside `/auth`, because everything else authenticates with the `Authorization: Bearer` header, which browsers never attach on their own.
* **Access tokens:** HS256 only (the verifier pins the algorithm, so `alg=none` and algorithm confusion are rejected), required claims `sub exp iat iss role jti`, expiry judged by the injected clock. Revocation of an access token is not possible; the 15-minute lifetime is the bound. Role changes sign the user out everywhere so the new role is picked up at the next login.
* **Passwords:** argon2id; length-first policy (10–128 characters, not derived from the email); hashes are upgraded transparently on login when parameters are strengthened. Login failures are indistinguishable and an unknown email still pays for one verification, so neither the message nor the timing reveals which emails exist. (Registration necessarily reveals a taken email with a 409.)
* **Brute force:** 5 failures per email in a fixed 15-minute window → 429 + `Retry-After`, even for the correct password; counters live in Redis under a hash of the email, so replicas share them and no address appears in a key.
* **Placement:** token/password primitives and the `current_principal`/`require_role` dependencies live in `core`; `Principal`/`Role` in `shared_kernel`. Features depend on those, never on `identity`, which keeps `identity` free of every other feature.
* **User-owned tables reference `users.id` with `ON DELETE CASCADE`** (same database). Another user's resource is reported as 404, never 403, so ids reveal nothing. Production refuses the development secret and any secret under 32 bytes.
